## Workflow structure
- `examples-perf.yml` has ONE job, `pages`, a 3-runner matrix (ubuntu-24.04, ubuntu-24.04-arm, macos-latest). No kernels job. Steps: `machine` (prints CPU), `conversion lowerings` (`node bench/lowering.mjs`, a micro-bench of i32/i64 truncation lowerings, printed to `lowering.log`), `pages` (`node examples/bench-pages.mjs`, `continue-on-error: true`, exits 1 when any page is not faster, so the log ends `##[error]Process completed with exit code 1` while the run is green), `summary`, artifact upload of `lowering.log` + `pages.log`.
- Triggers: push to main/branches touching `src/** module/** examples/** index.js interop.js package.json package-lock.json` and the workflow; `workflow_dispatch` with `opt` (jz optimizer overrides) and `pages`. Concurrency group is per ref, so a probe branch and main run in parallel.
- `bench.yml` (the "bench" workflow) has its own examples gate, a different harness: gate job runs `npm run test:bench` -> `test/bench.js` test "examples corpus" -> `examples/bench.mjs`. It times 25 examples (game-of-life, interference, ulam, mandelbrot, plasma, chladni, diffusion, waves, attractors, buddhabrot, lenia, raymarcher, rfft, zzfx, raytrace, marble, percolation, fern, boids, cloth, domain-color, epicycles, sandpile, swarm, blackhole), calling each module's exports directly (no page driver, no canvas), in microseconds per call, jz compiled with `optimize: 'speed'` vs the same source imported as ESM in V8. Exits non-zero if geomean <= 1 or a non-`opt` example is < 0.9x (FLOOR); prints `strict: N/M - not strict: ...`. On CI (`process.env.CI`) `okTiming` only logs "timing (informational on CI)"; the strict claim is asserted off-CI. Lines are in the bench.yml `gate` job step `npm run test:bench`. Of the pages below, only attractors, boids, swarm, lenia (and borderline blackhole) are in it. I did not fetch bench.yml logs.

## Harness (`examples/bench-pages.mjs`), what "JS time" is
- Node 24 (`setup-node 24`), no browser. One process per runner runs all pages sequentially. The page's inline `runDemo({size, load, frame, visit})` config is read from `examples/<name>/index.html`; DOM, canvas and 2D context are inert Proxies (canvas buffer writes go to the module's own `Uint32Array px`; nothing is drawn or uploaded). Canvas box fixed 1280x720 at DPR 1.
- JS = the example's `<name>.js` imported as an ES module and run on V8 (Ignition/Sparkplug/Maglev/TurboFan). jz = the same file compiled by `compileInternal` with `OPT` from `examples/build.mjs` (`optimize: 'speed'`), instantiated, run on V8's wasm tiers. Compile time not counted.
- Per page: JS first, then jz, back to back, same process, not interleaved. Each engine: `load`, then warm up to 400 frames or 1.5 s (jz follows the plan JS set: same warm count and batch size), then 7 batches of about 150 ms, median batch. So one sample of 7 batches per side per run, no paired rounds.
- The JS side goes first every time. Inference, not measured: any drift during a page (neighbour load, frequency) lands on the jz side.
- `lenia` frame only steps when `t - lastStep >= 1/20` and the harness advances t by 1/60 per frame, so its "ms/frame" averages one real step over three frames (inferred from the page config and `step`).
- `✗` means `sp > 1` is false. "1.00x" is shown for anything that rounds to 1.00, so a 1.00 row may be 0.996 or 1.004.

## 5. Leads (inference; nothing profiled or compiled)
- Transcendental-heavy hot loops: 6 of the 9 call `Math.sin/cos/atan2/exp/log` in the per-frame hot path: plume (about 9 per point x 40k), attractors (4 per iteration, millions), fireflies (1 `sin` per neighbour pair), ocean (`exp` per pixel, `cos/sin` per spectral cell), erosion (`log` and `sqrt` per pixel), lenia (1 `exp` per cell on top of the gather). jz ships its own fdlibm-based sin/cos (`0226a6d3e` 2026-10-28 "Compute sin and cos within an ulp of V8 ... by fdlibm's reduction and polynomials"; `1e907779c` "Shorten the fdlibm trig kernels' critical path"), so these pages run jz's trig, V8's JS runs V8's. Whether that is the cost here is not measured; I did not run any variant.
- `Math.random` per inner-loop step: 3 of 9 (maze, erosion, swarm). Not a majority; also non-stable-below pages call it in setup only (blackhole, lbm), so it is not the discriminator.
- Gather/scatter with data-dependent indexes and branches (no autovectorisable shape): maze, erosion, lenia, fireflies, boids: 5 of 9. Float-dense kernels (nbody, chladni, plasma, raymarcher, diffusion) win by 1.7-3.2x on x64 and macOS in the latest run (arm not checked). Inferred from ratios and source only.
- Small per-frame work: maze 0.9 ms, swarm 3 ms, boids 4 ms, erosion 4.5 ms: per-call overhead and the full-canvas fade/lerp pass (swarm, boids, maze: a pass over W*H pixels with a 3-channel lerp, no data dependence) are a larger share. Not measured.
- Architecture split: arm has 8 stable-below and x64 has 4 (the 4 are a subset of arm's 8 except lenia). Pages below on arm only: fireflies (tie on x64), swarm, boids, attractors, ocean (tie on x64): their ratio on x64 is 0.99-1.9. Suggests something arm-specific in the jz-wasm-on-V8 path (the repo's `bench/lowering.mjs` header says V8 "lowers the narrow form [i32.trunc_sat_f64_s] through extra checks on arm64"); a lead, not a finding.
- Three runner-level problems for anyone chasing: (1) x64 hardware changes per run: do not read one x64 run; (2) macOS has no signal at <20%; (3) JS runs first and jz second in one process, one 7-batch sample per side per run (pairing or alternation would cut noise; not in the harness today).
- What I would trust to chase: arm for the 8 pages and the sign of any change; EPYC 7763-labelled x64 runs for maze, lenia, plume, erosion. Both are cheap to check from the logs here.
